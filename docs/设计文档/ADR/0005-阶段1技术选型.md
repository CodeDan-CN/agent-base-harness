# ADR 0005：阶段 1 关键技术选型

- 状态：Accepted
- 日期：2026-08-18
- 所属阶段：阶段 1（Client 基础运行平台）

本 ADR 确认《阶段1-Client基础运行平台开发架构设计》第 11 节列出的五个阶段内决策。
这些选择不改变阶段方案确认的进程边界、User Scope、单 SQLite 与宿主机 Skill 脚本方向。

## 1. SQLite 驱动

### 背景

需在 Runtime Worker（Node Worker Thread）内使用单 SQLite，要求同步短事务、WAL、
`PRAGMA foreign_keys` 与 `busy_timeout`，且能被单元/集成测试以临时数据库覆盖。

### 决策

使用 `better-sqlite3` ^11。官方 `node:sqlite` 在当前 Node 20 LTS 不可用（Node 22.5+ 才有），
不符合本机 Node 20.19 环境。

### 理由

- 同步 API 与阶段方案“短事务、外部调用期间不持有事务”高度契合。
- 预制二进制覆盖 Node 20 与主流 Electron ABI，无需维护自定义构建。
- 兼容 `WAL`、复合外键、`json_valid` CHECK 约束等阶段表结构要求。

### 影响

- 原生模块需在 Electron 环境 rebuild（`@electron/rebuild`，`npm run rebuild`）。
- 单元/集成测试在 Node 环境运行，直接使用 Node ABI 预制二进制。

### 替代方案

- `node:sqlite`：当前 Node 版本不可用，被否决。
- `sql.js`（WASM）：无 WAL/原生外键语义，被否决。
- `libsql`/`wa-sqlite`：为阶段 1 引入额外复杂性，被否决。

## 2. 首发操作系统与 Credential Store Adapter

### 决策

首发平台为 macOS（darwin）。Credential Adapter 使用系统 Keychain，
通过内置 `security` CLI（`add-generic-password` / `find-generic-password` / `delete-generic-password`）实现，
不引入额外原生依赖。SQLite 业务表只保存不可逆 `credential_ref`（`agent-client-harness:<userId>:<purpose>:<entityId>`）。

### 理由

- `keytar` 已停止维护，避免引入被弃用的原生依赖。
- `security` 复用阶段 1 已建立的受控子进程能力，无新原生模块。
- Keychain 由操作系统管理加密与解锁，满足“明文不进入 SQLite/Renderer/日志”。

### 影响

- Adapter 通过注入 `exec` 函数实现，可在不触碰真实 Keychain 的测试中验证参数与行为。
- 其他操作系统 Adapter 留待后续阶段，`CredentialStore` 端口保持不变。

### 替代方案

- `@napi-rs/keyring`：现代但引入新原生依赖，与 Electron ABI 需重新对齐，被否决（可后续评估）。
- 文件加密存储：密钥管理问题下放给应用自身，安全性弱于系统 Keychain，被否决。

## 3. Main/Worker 构建与开发热重载

### 决策

- Renderer 使用 Vite + `@vitejs/plugin-react` 构建与 HMR。
- Main / Preload / Worker 使用 esbuild 分别打包为 `dist/{main,preload,worker}/index.cjs`，
  以 `electron` 与 `better-sqlite3` 为 external。
- 开发模式：Renderer HMR；Main/Worker 变更触发受控重启（`scripts/dev.mjs`）。

### 理由

- 四入口分别构建，Node 依赖不进入 Renderer 产物。
- esbuild 打包速度快、配置简单，`external` 明确阻止 Node builtin 泄漏。
- 受控重启符合阶段方案“Main/Worker 受控重启、Renderer HMR”的边界。

### 影响

- 生产 `asar` 打包时 Worker/原生模块的解包拆分在打包阶段单独处理。

### 替代方案

- `electron-vite`：开箱即用但引入对主/预加载/Renderer 的隐式约定，控制力弱于显式 esbuild 脚本，被否决。
- `tsc` 直出 + `electron-rebuild`：输出多文件且需额外维护入口映射，被否决。

## 4. IPC Schema 代码源与运行时校验库

### 决策

使用 `zod` 作为 Stage 1 契约的单一来源：请求 Schema（Query/Command）、
响应契约（`bootstrapResultSchema` / `healthSnapshotSchema`）、运行时 `safeParse` 校验
与 TypeScript 类型（`z.infer`）同源。错误码为独立稳定枚举，与 Schema 解耦。

### 理由

- Renderer/Main/Worker 跨进程边界需要运行时校验，`zod` 提供类型与校验单一来源，避免双重维护。
- 支持 malformed payload、超大 payload、非法 sender 等负向契约测试。

### 影响

- 新增 Stage API 时在 `src/shared/contracts/` 一并更新 Schema 与错误码。

### 替代方案

- 纯 TypeScript 手写类型 + 手写守卫：双重维护且易漂移，被否决。
- `valibot` / `io-ts`：功能等同，`zod` 生态与团队熟悉度更高，被否决。

## 5. 结构化日志与轮转

### 决策

自研轻量结构化 JSONL Logger（`src/infrastructure/logging/`）：
字段（`requestId` / `userId` / `workerGeneration` / `errorCode` 等）、内置脱敏（注册 secret +
常见敏感形态正则）、按文件大小有界轮转（默认 1 MB × 5 份）。Main 与 Worker 分别写入
`main.log` / `worker.log`，避免跨进程写竞争。

### 理由

- 无第三方副依赖，轮转与脱敏语义可被单元/集成测试直接验证。
- 满足阶段方案“不记录 Credential、Prompt、消息正文、SQL、UI 可见堆栈”的硬约束。

### 影响

- 日志轮转、脱敏边界、requestId 关联均有对应测试（M12-002/003/007）。

### 替代方案

- `pino` + `pino-roll`：成熟但引入 Worker transport 与配置面，且轮转语义黑盒，被否决。
- `winston`：配置较重，脱敏需额外插件，被否决。
