# 测试规格与开发就绪门禁

> 状态：初始测试草案。项目不再设置独立阶段 0 或 D0 开发门禁；以下测试场景由各阶段技术落地方案按实际范围重新确认。

## 1. 目的

本文件在编码前定义“什么证据才能证明设计被正确实现”。阶段 1 建立测试 Harness，阶段 2～4 按本规格持续补齐；不得为了阶段演示降低不变量。

## 2. 测试层级

| 层级                | 主要对象                                                            | 外部依赖            |
| ------------------- | ------------------------------------------------------------------- | ------------------- |
| Schema/Contract     | Event、IPC、Manifest、Provider、ToolResult、配置 Snapshot           | 无                  |
| 单元                | Inbox、状态机、Projector、Registry、Reducer、校验器                 | Fake Clock/ID       |
| Repository Contract | SQLite 与内存实现的一致行为                                         | 临时 SQLite         |
| 集成                | Worker、SQLite、Credential fake、文件 staging、Provider fake server | 本地假服务          |
| 属性测试            | seq、作用域、状态转换、Projection 回放、并发顺序                    | 生成数据            |
| UI                  | 设置页、队列、执行过程、用户切换和错误状态                          | 正式 Fixture        |
| E2E                 | 完整 Client 流程、重启、崩溃和安装包                                | Mock LLM/Tool/Skill |
| 手工兼容            | 真实 Provider、OS Credential、打包签名                              | 发布候选环境        |

## 3. 固定 Fixture 目录

阶段 1 应把以下文档场景固化为机器可读 Fixture；此处先定义名称和目的：

### 3.1 Runtime Event Fixture

- `text-completed-v1`：纯文本一次主模型调用。
- `single-tool-two-step-v1`：Tool Call、完整结果和一次后续 Step。
- `parallel-tools-ordered-commit-v1`：A/B/C 乱序结束、按 callIndex commit。
- `queue-after-turn-v1`：next-turn 在当前 Turn 完成后执行。
- `steer-at-safe-boundary-v1`：工具后注入下一 Step。
- `promote-queue-to-next-step-v1`：已持久排队的 next-turn 在不取消当前 Turn 的情况下原子提升到 next-step。
- `cancel-keep-queue-v1`：取消清理 next-step、保留 next-turn。
- `interaction-form-v1`：表单请求、提交、继续。
- `model-max-output-v1`：截断事实不显示 completed。
- `context-budget-exceeded-v1`：完整工具结果无法放入时明确失败。
- `worker-interrupted-v1`：开放 Turn 修复与副作用不确定。
- `compaction-version-conflict-v1`：摘要候选不覆盖新 Exchange。

### 3.2 Configuration Fixture

- `model-management-empty-v1`
- `model-service-configured-v1`
- `model-discovery-diff-v1`
- `model-revision-conflict-v1`
- `skill-install-preview-v1`
- `skill-needs-authorization-v1`
- `skill-enabled-registry-v1`
- `skill-tool-name-conflict-v1`
- `skill-uninstall-with-lease-v1`
- `dual-user-config-isolation-v1`

### 3.3 UI Fixture

Fixture 类型必须来自正式 Query/Snapshot Contract，不复用 `reference_ui` 的 Mock 类型。至少覆盖 loading、empty、ready、partial、error、conflict、disabled、archived 和 interrupted。

## 4. 必须长期成立的属性

### 4.1 Session 与 Event

- `(userId, sessionId)` 内 seq 从 1 连续递增。
- Event batch 原子提交，不存在部分事件。
- 一个 Session 最多一个开放 Turn。
- 一个 Step 最多一个 ModelRequest。
- 已完成 Step 的每个 Tool Call 恰好一个 Tool Result。
- Tool Result Event 与 Surface 内容逐字段相同。
- 一个 InboxItem 不能同时存在于 next-turn 和 next-step。
- Queue Item 提升前后保持同一 ID；promote/claim 竞态只能有一个成功，失败路径不得丢失消息。
- 实时 Projection 与从 seq 1 回放的 Projection 相同。

### 4.2 Context

- 自动投影不展开已闭合 Turn 的工具轨迹。
- 当前 Turn 的 Tool Call/Result 不拆散。
- Summary 与 raw Exchange 覆盖范围不重叠。
- promptEpoch 相同的稳定前缀字节一致。
- Provider usage 不与估算 token 重复统计。
- 上下文不超过 ModelConfigSnapshot 的硬预算。

### 4.3 用户隔离

- 所有用户私有实体恰好属于一个 LocalUser。
- 随机替换任意 Query/Command ID 为另一用户实体时，结果是 NOT_FOUND/FORBIDDEN_SCOPE，且不泄露存在性。
- 跨用户复合外键插入失败。
- 用户切换后旧用户增量不能进入新用户 Reducer。
- 用户 A 配置变更不能改变用户 B revision、Registry、promptEpoch 或 Credential namespace。

### 4.4 配置快照

- 同一 Step 的 Model、Skill 和 Runtime Snapshot 在执行期间不可变。
- revision 变化只影响下一个安全边界。
- Snapshot 不包含 secret 明文。
- 相同事实表和 revision 在重启后生成语义一致 Snapshot。
- 无有效默认模型时不静默 fallback。

### 4.5 Skill

- 未校验、未授权、未启用、不兼容或冲突 Skill 不进入 Registry。
- 安装失败不产生可执行半安装目录。
- 包 digest 不匹配时拒绝执行。
- 升级扩权必须重新确认。
- 活动 lease 释放前不能物理删除包。
- 导出包不包含配置、授权和 secret。

## 5. 双用户负向测试矩阵

对 Session、Event、ConversationEvent、ModelService、Model、SkillInstallation、SkillSettings、Attachment 和 Credential ref，至少测试：

1. 用户 A 创建实体。
2. 用户 B 使用相同 ID 查询。
3. 用户 B 尝试更新、删除、设为默认或建立关联。
4. 用户 B 订阅 A 的 sessionId。
5. 用户 B 使用 A 的 modelId 提交输入。
6. 用户 B 使用 A 的 Skill/Attachment 引用。
7. 直接 Repository 与经 Bridge 两条路径结果一致。
8. 安全日志记录拒绝，但 UI 不泄露另一用户实体详情。

## 6. Model Management 测试

- Service URL 和保留 header 校验。
- Credential replace/clear 的补偿事务。
- 连接成功、auth、timeout、network、protocol、capability 错误分类。
- discoveryToken 过期、跨用户、服务版本变化和重复应用。
- 发现结果不覆盖手工 contextWindow/能力。
- 默认模型必须有效、同用户且 Agent 可用。
- 服务/模型引用保护与历史展示。
- 模型切换发生在流式响应、工具运行和 stopping check 各时点的快照行为。

## 7. Skill 安全测试

恶意包语料至少包含：

- `../`、绝对路径、NUL、超长路径。
- 符号链接、硬链接、设备文件。
- 高压缩比 zip bomb、超文件数和超深目录。
- 大小写/Unicode 规范化后重名。
- 缺少/重复 `skill.json`、`SKILL.md`。
- 非法 SemVer、非法 skill/tool name。
- 远程 JSON Schema `$ref`、递归/超大 Schema。
- entry 逃离 scripts 根。
- 未声明 secret、权限或 host。
- Tool 名称与内置/其他 Skill 冲突。
- digest 在 inspect 与 commit 之间改变。

所有语料必须在执行任何包代码前得到确定拒绝结果。

## 8. Provider 与 Tool Contract

Provider fake server 覆盖：

- 正常文本流与多字节 chunk。
- 单/多 Tool Call 增量。
- usage、cache 和 reasoning 字段缺失/存在。
- 认证、限流、5xx、超时、断流和取消。
- finish reason 截断和未知值保留。
- 模型列表支持/不支持和畸形响应。

Tool Contract 覆盖：

- input/output Schema 双向校验。
- success、needs_input、retryable_error、fatal_error、cancelled。
- AbortSignal 与 timeout。
- parallel-safe 重叠执行、exclusive 屏障和顺序 commit。
- 完整结果、分页字段和 context budget failure。
- replaySafe/idempotency 与 unknown_side_effect 恢复。

## 9. IPC 与安全测试

- 任意 channel、未知 Command/Query 和超大 payload。
- sender origin/window 不匹配。
- Renderer payload 伪造 userId、credentialRef、绝对路径或 executable。
- 文件 token 过期、用途错误、跨窗口、跨用户和重复消费。
- Worker 返回非法 Schema。
- 用户切换与迟到响应竞态。
- unsubscribe 后仍收到事件视为失败。
- CSP、导航、新窗口和 Node API 暴露检查。

## 10. 崩溃注入矩阵

在下列边界强制终止 Worker：

- Input 接纳事务前/后。
- claim 后、`user.message` 前。
- `turn.started` 后。
- 模型 chunk 中。
- Tool Call 写入后、工具执行前/中/完成后、Result commit 前。
- 多工具部分完成时。
- Interaction 等待时。
- Summary 模型调用中和 version commit 前。
- Skill 文件发布后、数据库 commit 前。
- Credential 新值写入后、SQLite ref commit 前。

每个场景验证：事件不被改写、Queue 不丢失、Projection 可重建、非 replay-safe 副作用不重放、配置/文件补偿可完成。

## 11. UI 与视觉验收

- 会话、聊天、执行过程、输入和队列符合 reference_ui 关键比例。
- 模型页面覆盖服务列表、详情、凭据状态、测试、发现、手工模型和默认模型。
- Skill 页面覆盖搜索、已启用筛选、安装状态、详情、权限、启停和卸载。
- 不使用定时器或本地数组伪造永久成功状态。
- 所有持久状态可在刷新、用户切换和 Worker 重启后恢复。
- 键盘、焦点、Esc、表单错误、loading 和 disabled 状态可操作且一致。
- 已保存 secret 不回显。

## 12. 阶段验收参考

项目没有统一的 D0 开发就绪门禁。每个阶段开始后先完成该阶段完整技术落地方案，确认本阶段的 Contract、Fixture、测试范围和 ADR，然后进入实现；阶段完成时按该方案验收。

### 阶段 1 完成

- 工程、四个入口、Bridge、Worker、SQLite、Credential fake 和 staging 正式底座可运行。
- migration、Repository Contract、双用户负向测试和 IPC Schema 通过。
- 正式 Fixture 类型和 Headless Harness 建立。

### 阶段 2 完成

- Runtime 文档全部单元、属性、并发、上下文和恢复标准通过。
- ModelConfigSnapshot 与 SkillRegistrySnapshot 在 Headless 场景中完整工作。

### 阶段 3 完成

- 正式 UI 无生产 Mock 分支。
- 会话、模型和 Skill 核心 E2E 通过。
- 视觉状态与正式业务状态一致。

### 阶段 4 完成

- 模型能力目录、DeepSeek/百炼供应商预制和思考设置通过验证。
- 基于实际上下文容量的压缩、溢出恢复、数据库升级和 Projection 重建通过验证。
- 长 ConversationEvent、大 Tool Result、多 Session 和双用户定向集成用例通过。

## 13. 后续阶段需按需确认的选型

以下实现相关事项不集中在开发前一次性确认，而是在对应阶段技术落地方案中确认：

- 首发操作系统与发布范围。
- SQLite 驱动和 migration runner。
- OS Credential Store 库。
- Runtime Worker 原生依赖打包方式。
- 宿主机 Skill 脚本执行的命令确认、环境变量和工作目录策略。

这些待决策项不得弱化总体方案已经确认的 User Scope、进程边界和安全语义。
