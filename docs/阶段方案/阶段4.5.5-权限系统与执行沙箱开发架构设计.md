## 1. 文档目的

本文档定义 Agent Client 第一版权限体系，覆盖第一方文件工具、Bash、stdio/远程 MCP、运行时审批、用户问答、事件审计、恢复和 UI。它将阶段 4.5 已交付但分散存在的路径约束、MCP 工具目录和 Credential 隔离，收敛为一套可解释、可执行、可审计、可恢复的权限模型。

本阶段借鉴 deepseek-harness 的关键设计：Session 生效权限预设、三档文件写入沙箱、执行前 allow/deny/ask 决策、同一 Tool Call 等待审批和独立的用户问题通道。同时根据当前项目已有的用户级 MCP Catalog、Schema digest、Skill 加入状态、Session Event Log、Worker/Bridge 边界做适配，不照搬其目录结构或默认安全假设。预设的实际执行事实仍固定在 Session，但同一用户新建 Session 会继承该用户最近一次主动设置的预设。

本文是实施冻结文档。阶段 4.5.5 完成后，阶段 5 才冻结 Release Candidate。

## 2. 结论摘要

阶段 4.5.5 只新增三个彼此独立的运行机制：

| 层次                          | 回答的问题                               | 生命周期           | 典型结果                                                        |
| ----------------------------- | ---------------------------------------- | ------------------ | --------------------------------------------------------------- |
| 用户信任模式 PermissionPreset | 用户愿意让 Agent 自动执行到什么程度      | 当前 Session       | approval-required、guarded、full-access                         |
| 执行沙箱 Sandbox              | 这次进程最多能修改主机上的哪些文件       | 单次 Tool Call     | read-only、workspace-write、danger-full-access                  |
| 调用审批 Execution Approval   | 当前这一笔已加入 Tool 的调用是否允许执行 | 单次或当前 Session | allowed-once、session-granted、rejected、cancelled、unavailable |
| 用户问答 User Question        | 模型缺少业务选择时，用户希望选哪个答案   | 当前 Turn          | answered、cancelled、unavailable                                |

这些概念必须使用不同的数据结构、事件、UI 文案和恢复规则。用户只在输入区选择一档统一信任模式，Runtime 再把它解析为文件沙箱、网络策略和 MCP 审批策略。用户回答“选择方案 A”不代表批准工具调用；Skill/MCP 点击“加入”只表示它进入当前用户的能力目录，不等于其每次调用都自动执行。

Skill/MCP 的“加入、移除、启停和 Schema 变化后重新加入”沿用阶段 3/4.5 已有产品链路，不在 4.5.5 新建 Capability Authorization、授权审批页或第二套持久化授权状态。

阶段 4.5.5 的默认产品策略为：

- 用户首次使用时的新 Session 默认 guarded；之后新建 Session 继承当前用户最近设置的预设。
- read、write、edit 在各自沙箱范围内无需额外弹窗。
- Bash 必须进入操作系统级文件沙箱；发生沙箱拒绝时返回明确错误，由用户主动切换 Session 访问范围后重新发起。
- MCP Tool 不再向用户暴露逐工具审批频率；Runtime 只保留“自动 / 需批准”风险结果，历史 first-use 按“需批准”兼容读取。
- full-access 必须由用户主动切换并完成风险确认；该预设不再弹出执行审批，避免产生“全访问但仍可逐次兜底”的错误安全感。
- 审批失败、审批服务不可用、审计事件落库失败和沙箱提供器不可用全部 fail closed。

## 3. 实施前项目基线评估

### 3.1 已经具备的能力

| 现有能力                       | 当前实现效果                                                                        | 可复用部分                             |
| ------------------------------ | ----------------------------------------------------------------------------------- | -------------------------------------- |
| ScopedFileSystem               | read/write/edit 限制在 Session workspace，包含 realpath、符号链接、大小和读后写校验 | 作为第一方文件工具的内层路径守卫       |
| ShellExecutor 与 ProcessRunner | cwd 限制为 Session workspace，具备超时、取消、输出上限和环境变量白名单              | 作为沙箱进程启动器的执行基础           |
| Electron Renderer 安全配置     | nodeIntegration 关闭、contextIsolation 和 renderer sandbox 开启                     | 保持 UI 与主进程隔离                   |
| MCP Server/Tool Catalog        | Tool 点击加入后进入目录；记录 schema_digest，Schema 变化后需重新加入                | 作为既有能力目录入口，不新增授权层     |
| MCP 执行复核                   | 调用时复核用户、公开名称、enabled、review_status 和 schema digest                   | 防止目录快照漂移与越权路由             |
| MCP 网络与 Credential 控制     | 远程 URL 校验、SSRF 防护、Credential 引用隔离                                       | 继续作为远程连接安全边界               |
| Interaction 事件               | Runtime 可以请求用户输入并进入 awaiting_user                                        | 复用于普通业务问答，不作为执行审批主体 |
| Skill 安装与启停               | 用户通过添加 Skill 和启停按钮管理能力                                               | 沿用现有加入逻辑，不新增权限步骤       |
| Session Event Log              | 已有 append-only 事件及 Projection 思路                                             | 记录权限预设、审批和 Session Grant     |

### 3.2 尚未达到的能力

| 缺口                                                | 风险                                                         |
| --------------------------------------------------- | ------------------------------------------------------------ |
| Bash 没有操作系统级沙箱                             | cwd 不是安全边界，命令仍可访问当前 OS 用户可访问的其他目录   |
| ProcessRunner 仍传入真实 HOME 等环境                | 子进程可能发现并读写工作区外的用户状态                       |
| 仅终止直接子进程                                    | 子孙进程可能在取消或超时后继续运行                           |
| ToolScheduler 没有统一 pre-execute 权限门           | Built-in、Skill、MCP 各自形成分散规则，无法统一审计          |
| 现有 Interaction 不能挂起并恢复同一 Tool Call       | 若用于审批，只能结束 Turn 后重试，无法保证参数与调用身份不变 |
| MCP 审核只解决“能否进入目录”                        | 未解决某一次外部副作用调用是否需要用户确认                   |
| Skill permission_grants_json 缺乏统一语义与执行复核 | 字段存在但不能形成真实安全边界                               |
| 权限决策没有统一错误码和审计链                      | UI、恢复、测试难以区分拒绝、取消、不可用和沙箱阻止           |
| 沙箱、MCP 审核和用户问答 UI 容易混用“授权/允许”     | 用户无法理解自己授予的是长期能力还是单次动作                 |

### 3.3 必须明确的边界

Electron Renderer 的 sandbox 只保护 UI 进程，不是 Agent Tool 的执行沙箱。ScopedFileSystem 只约束使用该服务的第一方文件工具，不能约束 Bash、Skill 脚本或 MCP Server 子进程。远程 MCP 的副作用发生在外部系统，主机文件沙箱无法控制它。

因此，阶段 4.5.5 不能把现有能力描述成“已完成沙箱”；准确表述应是“第一方文件工具已具备工作区路径约束，执行进程沙箱待本阶段完成”。

## 4. 目标、非目标与威胁模型

### 4.1 阶段目标

1. 为每个 Session 保存一份可追溯的权限预设。
2. 所有 Tool Call 在执行前经过统一的权限决策管线。
3. 对 Bash 和 stdio MCP 子进程实施文件写入沙箱。
4. 沿用 MCP/Skill 的加入、移除和启停，不增加重复授权流程。
5. 支持同一 Tool Call 原地等待、一次性批准、拒绝、取消和恢复。
6. 将模型业务问答与系统执行审批彻底分离。
7. 权限事实进入 Event Log，可重建 Projection，可诊断且不泄露敏感参数。
8. 对 Worker 崩溃、Client 重启、Schema 变化、重复审批和审计失败给出确定行为。
9. 提供非技术化、语义一致的 UI。

### 4.2 本阶段非目标

- 不提供容器、虚拟机或完整系统调用隔离。
- 不保证阻止进程读取所有主机敏感文件；本阶段沙箱核心目标是控制文件修改范围。
- 不实现网络域名级、端口级或流量级沙箱。
- 不控制远程 MCP 服务端内部如何执行，只控制连接资格、目录暴露和每次调用同意。
- 不实现跨 Session 的“永远允许此动作”。
- 不实现沙箱拒绝后的自动提权与原调用重放；用户需主动切换访问范围后重新发起。
- 当前 Skill 只作为上下文内容加载，不提供独立脚本执行入口，因此不新增 Skill 脚本审批层。
- 不实现企业 RBAC、组织管理员策略、多人共享工作区和中央策略下发。
- 不让 LLM 自己批准权限，也不根据信任模型输出自动降低风险。
- 不在阶段 4.5.5 引入 Agent Profile 级、组织级权限模板或策略下发；用户级只保存“新 Session 创建默认值”，不作为运行中 Session 的跨会话提权通道。

### 4.3 受保护资产

- 用户工作区外的文件与目录。
- Session workspace 内的代码与数据。
- MCP/Provider Credential。
- 用户级 MCP 配置、Skill 安装内容和外部记忆数据。
- Tool Catalog 的身份、Schema 与路由一致性。
- 用户对外部系统执行副作用的知情同意。
- 权限审计的完整性和不可抵赖性。

### 4.4 主要威胁

- 模型或 Prompt Injection 诱导 Bash 修改工作区外文件。
- Bash 通过绝对路径、符号链接、子进程、HOME、临时目录或工具链逃逸。
- 已加入 MCP Tool 在 Schema 变化后继续使用旧 Session Grant。
- 恶意 MCP 描述伪装成低风险工具。
- 审批展示参数与实际执行参数不一致。
- 审批后 Tool Call 被替换、重排或重复执行。
- Worker 崩溃后自动重放具有副作用的已批准调用。
- 多 Session 或多用户串用审批、Catalog、Credential 或进程。
- 将普通问题的“确认”误当成系统权限。

## 5. 权限领域模型

### 5.1 核心类型

| 类型               | 值                                                              | 说明                   |
| ------------------ | --------------------------------------------------------------- | ---------------------- |
| PermissionPreset   | approval-required、guarded、full-access                         | 用户可见的统一信任模式 |
| SandboxMode        | read-only、workspace-write、danger-full-access                  | 文件修改边界           |
| ToolApprovalPolicy | never、always                                                   | Runtime 内部风险结果   |
| PreExecuteDecision | allow、deny、ask                                                | 执行前策略计算结果     |
| ApprovalOutcome    | allowed-once、session-granted、rejected、cancelled、unavailable | 用户或系统最终决策     |

### 5.2 Tool 调用身份

权限不能只绑定展示名称，必须绑定稳定身份：

| 能力类型       | 权限身份组成                                                     |
| -------------- | ---------------------------------------------------------------- |
| 第一方 Tool    | toolName（当前内置定义随应用版本发布）                           |
| MCP Tool       | userId + serverId + rawToolName + schemaDigest                   |
| 单次 Tool Call | sessionId + turnId + toolCallId + ToolIdentity + argumentsDigest |

任何身份字段变化都会使旧 Session Grant 失效。MCP Tool 的描述文本来自不受信任服务，不参与风险判定和身份生成。

### 5.3 权限作用域

- 用户级：MCP/Skill 加入状态、ToolApprovalPolicy、新 Session 继承的最近 PermissionPreset。
- Session 级：PermissionPreset 与待处理审批；不再创建新的首次调用 Grant。
- Turn 级：待审批队列。
- Tool Call 级：参数摘要和最终 ApprovalOutcome。

Session 创建时从当前用户的新会话默认值复制一份固定 PermissionPreset；用户首次初始值为 guarded。任一空闲 Session 主动切换预设时，同一事务内更新该 Session 与当前用户的新会话默认值。已存在的其他 Session 不回写，其他用户不受影响。运行中的 Turn 不允许切换；用户停止当前 Turn 后才能修改 Session 预设。

## 6. 产品预设

| 用户选项          | 基础 SandboxMode   | 工作区   | 工作区外                         | 网络                          | MCP                                      |
| ----------------- | ------------------ | -------- | -------------------------------- | ----------------------------- | ---------------------------------------- |
| approval-required | workspace-write    | 自动读写 | 读取允许；写入按精确路径逐次批准 | 每个需要网络的 Tool Call 批准 | 默认每次批准                             |
| guarded           | workspace-write    | 自动读写 | 读取允许；写入仍需批准           | 低风险自动，高风险批准        | 读取类可配置自动；修改、发送、删除类批准 |
| full-access       | danger-full-access | 自动读写 | 按当前 OS 用户权限访问           | 自动                          | 自动，不再询问                           |

风险判断必须来自 Runtime 的确定性 Tool 元数据和结构化参数：第一方工作区读写是低风险；声明联网或工作区外写入是高风险；MCP 在 Runtime 内归为 `never / always`。禁止让模型根据描述文本自行决定是否需要审批。

### 6.1 默认值

- 新用户的首个 Session 默认 guarded。
- 同一用户后续新建 Session 继承其最近一次在任一 Session 主动设置的预设，包括 full-access。
- 继承只发生在创建时；已存在的其他 Session 保持原预设，不跨用户同步。
- 历史 `read-only / workspace-write / danger-full-access` 分别映射为 `approval-required / guarded / full-access`。
- 切换到 approval-required 或 guarded 在 Session 空闲时立即生效。
- Turn 正在执行时不允许普通切换；用户可以先取消 Turn，再切换。
- full-access 首次或再次由用户主动切换时必须显示风险说明和独立确认勾选，不允许由模型或深链直接开启。新 Session 继承用户已确认的该预设时不重复弹窗，但输入区必须明确显示“完全访问”。

### 6.2 UI 文案约束

- approval-required 显示“请求批准”。
- guarded 显示“受控自动”，并标记为推荐。
- full-access 显示“完全访问”。
- 不使用“安全”“绝对隔离”等无法兑现的词。
- 完全访问说明必须包含：仍以当前登录用户身份运行、可能访问工作区外文件、不会再逐次弹出权限审批。

## 7. 统一执行前权限管线

所有第一方、Skill 和 MCP Tool Call 使用同一顺序：

1. 从当前 Step 读取不可变 ToolCatalogSnapshot 与 PermissionSnapshot。
2. 校验 Tool Call 的名称、参数 Schema、用户、Session 和目录 generation。
3. 解析 ToolIdentity 与 normalizedArgumentsDigest。
4. 确认 Tool 仍处于当前用户已加入且启用的目录；这属于既有目录一致性检查，不产生新的授权步骤。
5. 由 Tool Policy 产生 allow、deny 或 ask。
6. 应用不可放宽的硬守卫：用户隔离、Schema digest、路径、Credential、URL/SSRF、能力撤销。
7. 若为 deny，记录拒绝并返回确定错误。
8. 若为 ask，先持久化 approval.requested，再挂起同一 Tool Call。
9. 收到有效决策后先持久化 approval.resolved，再释放调用。
10. 解析本次 SandboxExecutionPolicy，启动沙箱提供器。
11. 执行 Tool，记录 Tool Result、退出事实和有界输出。
12. 若发生沙箱拒绝，返回 SANDBOX_DENIED 或进程退出事实，不自动提升权限或重放调用。

### 7.1 单调性原则

策略插件或具体 Tool 可以把 allow 收紧为 ask/deny，也可以把 ask 收紧为 deny，但在通过全局 pre-execute 之后，任何后置守卫都不能把 deny 放宽为 allow。

以下规则永远不能被用户审批绕过：

- 跨用户访问。
- Tool 已移除、停用或 Schema changed。
- Tool Call 与快照身份不一致。
- MCP 路由、Credential 引用或 URL 校验失败。
- Approval 对应的参数摘要与实际参数不一致。
- 过期、重复或不属于当前用户的审批。

### 7.2 并发规则

- 单个 Session 的权限审批按模型产生 Tool Call 的顺序串行展示。
- 等待审批的 Tool Call 不占用执行槽，但保留 Turn。
- 同一批并行 Tool Call 中，已明确 allow 的调用是否先执行由 Runtime 现有调度语义决定；具有副作用的审批调用默认形成屏障，避免用户在未知前序结果下批准后续动作。
- 每个 approvalId 只能终态一次；重复响应返回 APPROVAL_STALE。
- 不允许一个 Session 的批准解锁另一个 Session。

## 8. Tool 默认策略

| Tool 类型            | 进入目录的既有条件                  | 默认调用审批                                     | 沙箱                                                |
| -------------------- | ----------------------------------- | ------------------------------------------------ | --------------------------------------------------- |
| read                 | 第一方固定能力                      | never                                            | 工作区外读取按当前 OS 用户读取权限                  |
| write/edit           | 第一方固定能力                      | 工作区内 never；工作区外 always                  | 只为批准的精确外部路径放行                          |
| bash                 | 第一方固定能力                      | 本地工作区 never；联网或外部写入 always          | 受限模式默认禁网，外部写路径显式声明                |
| Skill 文档           | 用户已添加并启用                    | never                                            | 只读加载                                            |
| 新加入 MCP Tool      | 用户点击加入且 schema digest 未变化 | guarded 按 Runtime 风险分类；请求批准强制 always | 远程调用不受本地文件沙箱；stdio Server 进程另行沙箱 |
| 未知第三方 MCP Tool  | 同上                                | always                                           | 同上                                                |
| 内置 Memory MCP Tool | 同上                                | 读取工具 never；修改工具 always                  | stdio Server 使用托管目录沙箱                       |

需批准的调用只提供“允许这一次”“拒绝”和“取消”，不提供“本 Session 允许”。

## 9. 执行沙箱

### 9.1 沙箱保护对象

阶段 4.5.5 的 PermissionPreset 先解析为每次调用的 SandboxMode。approval-required 与 guarded 默认使用 workspace-write；full-access 使用 danger-full-access。声明工作区外写入并完成审批后，只为当前精确 Tool Call 增加所批准的写入路径。

底层 SandboxMode 控制文件系统修改能力：

- read-only：不允许 Tool 子进程对项目和主机产生文件修改。
- workspace-write：只允许修改当前 Session workspace 与系统为本次调用创建的精确临时目录。
- danger-full-access：不施加文件路径沙箱，但仍受当前 OS 用户权限、最小环境、超时、取消、输出上限和 Tool 目录约束。

受限模式默认禁止 Bash 网络访问；只有 Tool 参数明确声明需要网络且执行审批通过后，当前 Tool Call 才开放网络。它仍不承诺：

- 阻止所有文件读取。
- 隔离所有非 Bash 宿主网络活动。
- 限制 CPU、内存或所有系统调用。
- 隔离远程 MCP 服务内部行为。

产品文案必须称为“文件访问范围”或“执行访问范围”，不能暗示完整虚拟机安全。

### 9.2 不同模式的目录规则

| 目录              | 请求批准                             | 受控自动                             | 完全访问               |
| ----------------- | ------------------------------------ | ------------------------------------ | ---------------------- |
| Session workspace | 读写                                 | 读写                                 | 按 OS 权限             |
| 本次调用 temp     | 读写                                 | 读写                                 | 按 OS 权限             |
| 工作区外读取      | 按 OS 读取权限                       | 按 OS 读取权限                       | 按 OS 权限             |
| 工作区外写入      | 精确路径逐次批准                     | 高风险，精确路径逐次批准             | 按 OS 权限             |
| Skill 安装目录    | 原始目录不修改；运行副本在 workspace | 原始目录不修改；运行副本在 workspace | 按 OS 权限             |
| MCP 托管数据目录  | 由具体 stdio Server 沙箱决定         | 由具体 stdio Server 沙箱决定         | 由具体 Server 策略决定 |

受限模式仍可能需要动态链接器、系统命令和包管理运行时读取系统文件，因此本阶段不宣称“机密读取隔离”。第一方 `read` 可以读取当前 OS 用户有权读取的工作区外常规文件；第一方 `write/edit` 只有在 full-access 或当前精确路径审批通过后才能越界。

### 9.3 平台提供器

首发 macOS 由 ProcessRunner 统一编译并调用 Seatbelt profile。approval-required/guarded 的基础 profile 只开放 Session workspace 与该 Tool Call 的临时目录写入，并默认 deny network；已批准的工作区外路径和网络能力只加入当前 Tool Call。full-access 不包裹 Seatbelt。

Linux/Windows 当前没有受限沙箱提供器。受限模式在这些平台确定性返回不可用，不静默退化；full-access 仍可按当前 OS 用户权限执行。

规则：

- approval-required/guarded 下提供器 unavailable 时 fail closed，禁止静默退化为完全访问。
- 普通命令退出与沙箱拒绝都保留 stderr/退出码供诊断；V1 不根据错误文本自动提权。

### 9.4 ProcessRunner 改造

ProcessRunner 必须接收每次调用解析后的 SandboxExecutionPolicy，而不是只接收 cwd：

- cwd 必须属于 Session workspace 或经过授权的托管目录。
- 使用最小环境变量集合；不把真实 HOME 作为默认运行 HOME。
- 为调用创建 Session/ToolCall 专属临时 HOME 和 temp，并按模式配置写权限。
- PATH 使用应用冻结的安全来源与必要系统路径，不接收模型提供的 PATH。
- Credential 只按 Tool Adapter 明确注入，不进入通用 Bash 环境。
- 启动独立进程组；取消、超时和 Worker 退出时终止整个进程树。
- 限制 stdout/stderr 大小，保留截断事实。
- 记录 executable、cwd、模式、提供器与退出分类，不记录敏感环境值。

### 9.5 沙箱拒绝后的处理

V1 不实现单次沙箱升级。受限执行被阻止后，该 Tool Call 结束，不自动重试。用户可以查看错误，停止当前 Turn，在输入区主动切换 Session 访问范围，再让 Agent 发起新的 Tool Call。这样避免首次调用已产生部分副作用时被宿主自动重放。

## 10. 执行审批

### 10.1 与现有 Interaction 的关系

现有 interaction.requested/interaction.resolved 继续服务业务确认、表单和普通问题。执行权限新增独立的 approval.requested/approval.resolved：

- Approval 会挂起原 Tool Promise，同一 Tool Call 原地恢复。
- Interaction 可以结束当前模型回合并等待下一条用户输入。
- Approval 卡片具有系统来源、不可由模型伪造的样式。
- 模型文本中的“请点击允许”不具有任何权限效果。

### 10.2 ApprovalRequest

请求至少包含：

- approvalId、userId、sessionId、turnId、stepId、toolCallId。
- toolType、ToolIdentity、展示名。
- ToolApprovalPolicy 与请求原因。
- 参数的结构化安全摘要和 argumentsDigest。
- 目标资源摘要，例如路径、域名、MCP Server。
- 可选决策集合。
- createdAt。

原始 Credential、完整环境变量和可能包含秘密的未裁剪参数不得进入 ApprovalRequest。Adapter 必须提供安全摘要器；无法安全摘要的参数仅显示字段名、类型和 hash。

### 10.3 决策顺序

审批通过的原子语义是：

1. 校验用户、Session、内存中同一 Tool Call 的 pending 状态和 idempotencyKey。
2. 在事务中追加 approval.resolved。
3. 如选择 Session Grant，同时追加 permission.grant.created。
4. 提交事务。
5. Runtime 收到已提交的决策后释放 Tool Call。

如果事件持久化失败，调用不得执行。先执行后记审计是禁止行为。

### 10.4 可用结果

| 结果            | 行为                                                              |
| --------------- | ----------------------------------------------------------------- |
| allowed-once    | 仅当前精确 Tool Call 执行一次                                     |
| session-granted | 当前 Tool Call 执行，并对相同 ToolIdentity 建立当前 Session Grant |
| rejected        | 当前 Tool Call 返回 APPROVAL_REJECTED                             |
| cancelled       | 当前 Tool Call 返回 APPROVAL_CANCELLED                            |
| unavailable     | UI/Worker/审批服务不可用，fail closed                             |

### 10.5 超时与恢复

- V1 审批默认不做短时间自动超时；Session/Turn 被取消、关闭或 Worker 退出时转为 unavailable。
- Client 重启后，未释放执行的审批可恢复展示，但原 Worker 内存中的 Tool Promise 已不存在，因此旧审批统一终结为 unavailable。
- 具有副作用的 Tool Call 不因恢复自动重放。
- 用户可以在新 Turn 中让模型重新发起动作，形成新的 toolCallId 和 approvalId。

## 11. MCP 加入与调用审批设计

### 11.1 沿用“加入工具”

MCP Tool 继续通过现有“加入/移除”按钮决定是否出现在 Agent 工具目录。enabled、review_status、schema_digest 只是该产品链路的目录事实，不再被描述为一套独立权限系统。新增 ToolApprovalPolicy 后，执行已加入 Tool 时再次复核：

- userId 与 Server 所属用户。
- Server enabled、Tool enabled。
- review_status 为 approved。
- 当前 schema_digest 等于 Snapshot 和 ToolIdentity 中的 digest。
- publicName 与 rawToolName 路由一致。
- Credential 引用有效且属于同一用户。

任何目录一致性失败都直接停止调用，不能通过单次审批绕过；用户只需回到 MCP 页面重新加入，不进入新的授权页面。

### 11.2 MCP 调用审批

V1 不根据服务端 Tool description 自动判定风险。默认：

- 未知第三方 Tool 点击加入后按 always 执行。
- 用户界面只保留加入/移除开关，不再显示逐工具审批频率下拉框。
- 可信内置 MCP 可以由 Client 固定清单把纯读取 Tool 标为 never；修改、删除和创建 Tool 固定为 always。
- V1 不根据第三方名称或描述自动降级风险，避免服务端描述影响可信决策。
- Schema 变化后 review_status 变为 changed，旧审批策略和 Session Grant 均不可继续放行。

### 11.3 stdio MCP Server 沙箱

stdio MCP Server 是本地主机进程，不能只依赖其 cwd：

- 默认运行在“托管数据访问”策略：应用包资源与 Server 安装目录只读，只允许写入该 Server、该用户的 managed data 目录和精确 temp。
- 默认不允许写 Session workspace。
- Server 进程使用最小环境和专属 HOME，Credential 仅注入该 Server。
- 连接关闭、超时、重启预算和日志脱敏沿用现有 MCP Manager/SDK 生命周期。
- Server 沙箱提供器 unavailable 时，该 Server 进入 blocked，不静默全权限启动。

V1 不提供 stdio Server 的主机访问范围切换。需要直接读写项目的本地 MCP Server 暂不支持，后续若引入必须单独设计风险确认，不能复用“加入工具”开关暗中扩大主机文件范围。

### 11.4 远程 MCP

远程 MCP 不受本地主机文件沙箱控制。保留现有 SSRF、URL、Credential 与用户隔离，并通过 Execution Approval 提供用户同意。UI 必须说明“批准代表同意向该外部服务发起此次调用”，不得显示为“已在沙箱中安全执行”。

## 12. Skill 权限设计

Skill 点击添加并启用后即可进入当前用户的能力目录，不再弹出第二次能力授权。当前实现只把 Skill 指令与只读资源加入上下文，不直接产生独立 Tool Call。

规范化规则：

- authorization_status 与 permission_grants_json 不再扩展为新权限模型，仅保留现有数据兼容。
- 当前 Skill 作为指令与只读资源进入上下文，不注册独立可执行 Tool，因此没有额外审批按钮。
- Skill 需要外部能力时只能调用当前目录中已加入的 Tool，并由该 Tool 自身的沙箱或调用审批规则决定。
- Skill 文本不能声明“无需审批”“完全访问”等越过宿主策略的指令。

## 13. 用户问答

模型在缺少业务信息时使用 User Question，不使用 Approval：

- 单选、多选、自由输入和计划确认均属于业务问答。
- 问题可以由模型生成，审批卡片只能由可信 Runtime 生成。
- 用户问题答案进入 Conversation/Event Context；权限审批结果不作为自然语言答案注入模型，只作为结构化执行结果。
- 用户问题不能创建 Permission Grant、改变 SandboxMode 或审核 MCP/Skill。
- delegated child Agent 在 V1 不直接向用户提问；由根 Runtime 汇总为 User Question。
- 普通问题记录为 pending Interaction；系统审批记录为 pending Approval，二者使用不同 Projection。

## 14. 事件、Projection 与快照

### 14.1 新增 Session 事件

| 事件                      | 关键字段                                                            | 用途                     |
| ------------------------- | ------------------------------------------------------------------- | ------------------------ |
| permission.preset.changed | from、to                                                            | 记录 Session 预设变化    |
| approval.requested        | approvalId、toolCallId、toolIdentity、argumentsDigest、presentation | 建立待审批事实           |
| approval.resolved         | approvalId、toolIdentity、resolution                                | 建立最终决策             |
| permission.grant.created  | approvalId、toolIdentity、scope                                     | 仅兼容历史事件，不再新增 |

事件 payload 只记录脱敏摘要、digest 和引用，不记录 Credential、完整 shell 环境或敏感 Tool 参数。

### 14.2 PermissionProjection

每个 Session Projection 至少包含：

- activePreset（来自 Session 列）。
- 历史 Session Grants 索引，仅用于旧事件投影。
- pendingApproval 队列。

审批必须能由 Event Log 重建；Session 的当前 PermissionPreset 由同一事务同时更新 Session 列并追加 permission.preset.changed 事件。

### 14.3 运行时状态

等待审批期间原 Tool Promise 保持挂起，Turn 仍为运行中；Projection 中独立的 pending Approval 负责驱动系统审批卡。用户问答仍使用 awaiting_user，二者不共用状态或事件。批准后继续同一 Tool Call；拒绝、取消或不可用则以 Tool Error 继续模型 Step。

## 15. SQLite V8 迁移

阶段 4.5.5 使用 schema version 8，迁移只向前执行。

### 15.1 mcp_tools

新增：

- `approval_policy` 是已发布 V8 物理列，仍允许 never、first-use、always；Domain 将历史 first-use 映射为 always，新写入只使用 never/always。

### 15.2 local_users 与 sessions

- `local_users.session_permission_preset` 与 `sessions.permission_preset` 是已发布物理列，继续保存兼容标识：`read-only / workspace-write / danger-full-access`。
- Domain/UI 映射为 `approval-required / guarded / full-access`；映射关系固定，不能由模型或配置改变。
- 新记录的默认物理值 `workspace-write` 对应用户语义 guarded。预设变化、`permission.preset.changed` 事件和用户新会话默认值在同一事务提交，避免 Session、用户默认值与审计事实分叉。

### 15.3 Skill 兼容

- 保留已有 authorization_status 与 permission_grants_json，阶段 4.5.5 不再扩展其语义。
- 已添加并启用的 Skill 保持可用；脚本首次实际调用时进入 Execution Approval。

## 16. Client、Bridge 与 Worker Contract

### 16.1 Commands

| Command               | 作用                                        | 必要校验                                                   |
| --------------------- | ------------------------------------------- | ---------------------------------------------------------- |
| permission.preset.set | 修改 Session 预设并更新该用户的新会话默认值 | 当前用户、Session 空闲、枚举值；完全访问由可信 UI 二次确认 |
| approval.resolve      | 提交审批决定                                | user/session/approval/未终态/idempotencyKey                |

MCP Tool 只提供启用/停用，不再提供独立的“首次询问”或审批策略设置；调用时是否需要批准统一由 Session 权限档位与 Tool 风险分类决定。

### 16.2 Queries

- session.list/session.snapshot：返回 Session permissionPreset 与审批 Projection。
- mcp-management.snapshot：返回 Catalog 加入状态、approvalPolicy 与 Schema 状态。
- 不新增独立权限设置源、待审批表或审计表查询；审批事实直接来自 Session Event Log/Projection。

### 16.3 Subscriptions

Session Snapshot 增加：

- permissionPreset。
- approvals 与 permissionGrants。

Bridge 只暴露结构化 DTO，不向 Renderer 暴露 EventStore、Credential、进程句柄或沙箱配置文件路径。

### 16.4 Worker 边界

审批请求通过现有 Session Event subscription 进入 Renderer；审批结果通过结构化 approval.resolve Command 回到 Worker。Renderer 不直接持有 Tool Promise、进程句柄或 Credential。

## 17. UI 与交互

### 17.1 输入区权限入口

聊天输入区显示当前权限 Chip：

- 请求批准。
- 受控自动（推荐）。
- 完全访问。

点击打开普通 Popover，展示三档解释。该 Popover：

- 点击外部自动关闭。
- Escape 关闭。
- 切换选项后关闭并更新下一 Step。
- Turn 运行中选项禁用并说明需先停止。
- 不出现浏览器默认蓝色 focus outline；使用设计系统 focus-visible 样式，键盘导航仍保留清晰可访问焦点。

### 17.2 完全访问确认

完全访问使用 Modal，不是普通 Popover：

- 点击遮罩不自动确认。
- 明确列出可访问工作区外文件、不再逐次审批、仍按当前 OS 用户运行。
- 用户勾选“我理解风险”后才能确认。
- 取消不改变现有预设。
- 新建 Session 若继承完全访问，不重复确认，但权限 Chip 不得隐藏或降级显示。

### 17.3 审批卡片

审批不是会消失的菜单。等待审批时：

- Composer 切换为系统审批卡片或在其上方固定显示。
- 显示可信 Tool 来源、Server/Skill、动作摘要、目标、审批原因和可选决策。
- 所有新审批只提供“允许一次”“拒绝”。
- 点击其他区域不关闭、不默认拒绝。
- 卡片只会在用户明确选择、Turn 取消或 Worker 恢复时消失。

### 17.4 MCP/Skill 设置

MCP Tool 行同时展示：

- 加入状态：未加入、已加入、Schema 已变化、已禁用。
- 原始名称、公开名称和描述。

调用审批由输入区三档信任模式统一控制，MCP 设置页不再出现第二套审批下拉框。

Skill 沿用现有添加/启停界面，不增加权限选项。

### 17.5 审计与恢复

V1 不新增独立审计页。approval.requested、approval.resolved、permission.grant.created 与 permission.preset.changed 进入 Session Event Log，可通过现有事件与诊断链路重建；UI 从 Session Snapshot 恢复待审批卡片。事件只保存安全展示摘要与 digest，不回显 Credential 或完整环境。

## 18. 错误模型

| 错误码                 | 含义                             | 是否可重试                 |
| ---------------------- | -------------------------------- | -------------------------- |
| PERMISSION_DENIED      | 硬策略拒绝                       | 修改配置/动作后            |
| APPROVAL_REJECTED      | 用户拒绝                         | 模型可选择替代方案         |
| APPROVAL_CANCELLED     | 用户或 Session 取消              | 新 Tool Call               |
| APPROVAL_UNAVAILABLE   | 审批通道或 Worker 恢复不可用     | 新 Tool Call               |
| SANDBOX_DENIED         | 文件、网络或路径不在本次授权范围 | 补充精确声明并重新发起审批 |
| SANDBOX_UNAVAILABLE    | 受限模式提供器不可用             | 修复环境或主动切完全访问   |
| MCP_TOOL_NOT_AVAILABLE | MCP Tool 未加入、已变化或已停用  | 重新加入                   |

Bash 被 Seatbelt 拒绝时保留进程退出码与有界 stderr；Runtime 不猜测并自动提升权限。Tool Error 返回给模型时提供安全、可行动的摘要；详细平台日志必须脱敏。

## 19. 安全不变量

1. 只有用户已加入并启用的 Skill/MCP Tool 进入 Tool Catalog。
2. Tool Call 执行时必须再次复核 ToolIdentity，不能只信模型看到的 Snapshot。
3. ask 决策未得到已持久化批准前，副作用不得开始。
4. Approval 不能放宽跨用户、Schema、Credential、URL 和路由硬守卫。
5. Session Grant 不跨 Session、不跨 digest、不覆盖 always。
6. 沙箱拒绝不自动提升 Session 预设，也不自动重放 Tool Call。
7. 受限模式的沙箱提供器 unavailable 时 fail closed。
8. Worker/Client 恢复不自动重放具有副作用的调用。
9. 用户问题答案永不形成权限授权。
10. Renderer 不能直接启动进程、读 Credential 或伪造审批终态。
11. 日志、事件和审批摘要不得保存 Credential 与敏感原始参数。
12. 用户隔离在 Host、Worker、Catalog、Approval、Sandbox 目录和 MCP 进程每层复核。

## 23. 迁移与发布策略

1. V8 migration 在启动阶段事务执行，失败则保留原库并阻止进入新 Runtime。
2. 历史物理值通过兼容映射读取：read-only→approval-required、workspace-write→guarded、danger-full-access→full-access，不改写旧 checksum，不伪造历史事件。
3. 历史 first-use 按 always 读取，降低升级后静默外部副作用风险。
4. 旧 Skill 字段保持兼容，不升级为新的权限事实。
5. 沙箱功能先在开发/内部包显示 enforcement；首发包受限模式 unavailable 必须阻断。
6. full-access 不作为兼容回退，也不因沙箱初始化失败自动启用。
7. 阶段 5 的备份、诊断、隐私说明、发布检查和已知问题必须纳入权限事件、MCP 数据与沙箱限制。

## 24. 风险与缓解

| 风险                                     | 缓解                                                                |
| ---------------------------------------- | ------------------------------------------------------------------- |
| macOS Seatbelt 在目标版本/签名包行为变化 | 先做 Spike，建立真实签名包 E2E 和 enforcement 事实                  |
| 文件沙箱被误解为完整安全隔离             | UI、文档和错误始终说明边界，不使用绝对安全措辞                      |
| 审批过多造成疲劳                         | 默认 workspace 文件操作不询问；受控自动只放行确定性低风险 Tool      |
| MCP Tool 风险声明不可信                  | 未知第三方 Tool 默认 always；只有可信内置只读能力可标记 never       |
| 首次受限执行可能产生部分副作用           | 宿主不自动提权或重放；用户调整权限后形成新的 Tool Call              |
| 审批与 Tool 参数 TOCTOU                  | 绑定 normalizedArgumentsDigest，执行前最终复核                      |
| Worker 崩溃导致重复外部副作用            | 未知结果不自动重放，旧审批转 unavailable                            |
| stdio MCP 长驻进程扩大访问范围           | 独立托管目录沙箱、专属 HOME、最小 Credential 与现有连接生命周期清理 |

## 25. 冻结决策

1. 阶段 4.5.5 固定实现 Sandbox、Execution Approval、User Question 三条主线。
2. 用户只看到请求批准、受控自动、完全访问三档；默认受控自动。
3. full-access 由用户主动确认，审批通道为 never，不提供虚假逐次兜底。
4. Bash 和 stdio MCP 必须进入 OS 文件沙箱；cwd 不视为安全边界。
5. Skill/MCP 点击加入后即进入能力目录，不新增 Capability Authorization；调用审批只处理具体 Tool Call。
6. MCP 设置页不暴露审批频率；未知第三方 Tool 默认需批准，可信内置只读 Tool 可由 Runtime 标记自动。
7. 审批挂起并恢复同一 Tool Call，审批事实提交后才能执行。
8. 不再创建新的 Session Grant；阶段 4.5.5 不实现“永远允许”。
9. 沙箱拒绝后不自动提权或重放；用户只能主动修改空闲 Session 的预设。
10. User Question 不能授予任何系统权限。
11. 受限沙箱不可用、审批不可用、审计失败一律 fail closed。
12. 崩溃恢复不自动重放具有副作用的 Tool Call。
13. 权限预设的同步最大边界是当前用户：任一 Session 主动设置后，仅同用户后续新建 Session 继承；已有 Session 和其他用户不受影响。
