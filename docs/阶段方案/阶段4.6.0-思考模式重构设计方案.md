## 1. 这次要解决什么

关闭模型思考之后，用户仍然能够看到简短的执行说明和真实工具状态；开启思考时，也不必在执行区域阅读长篇 reasoning。

采用 Codex 的分层原则：原生 phase 贯穿消息链路，缺失时保留兼容归类；配合简短提示词和执行过程展示。复用已有模型思考开关，不为说明生成增加独立模型调用。

| 内容           | 来源                                    | 展示位置                         |
| -------------- | --------------------------------------- | -------------------------------- |
| 执行说明       | 模型普通消息；优先使用原生 commentary   | 对应执行步骤                     |
| 工具状态和结果 | Runtime 的真实工具事件                  | 工具卡片                         |
| 最终回答       | 模型普通消息；优先使用原生 final_answer | 聊天正文                         |
| 模型推理       | Provider 返回的 reasoning               | 对应步骤中的可展开详情，默认折叠 |

不要求每一步都有说明。只有工具调用、没有普通文字时，显示工具卡片即可。

## 2. Codex 中借鉴什么

已检查本地 `/Users/codedan/local/project/codex-main` 源码：

- `codex-rs/protocol/src/models.rs` 定义了 commentary 和 final_answer，同时明确 Provider 可能不返回 phase。
- `codex-rs/protocol/src/prompts/base_instructions/default.md` 要求简短说明、合并相关动作、不为每个细小调用配旁白。
- `codex-rs/core/src/session/turn.rs` 的继续执行还依赖工具、待处理输入和生命周期信号，并非仅由消息 phase 决定。

本次借鉴“推理、说明、工具状态分离”和“原生 phase 可选、未知时兼容”的方式，不完整搬入 Codex 的协议和执行机制。

当前项目继续使用 Chat Completions。现有 Adapter 已兼容读取响应的 `message.phase` 和流式 `delta.phase`；未提供的路径保留兼容行为。这是对可选扩展字段的接收能力，不代表 Chat Completions 标准或已配置服务保证返回该字段。原生提前定位已用本地 HTTP/SSE Fixture 验证，未向用户真实模型发起额外请求，实际端点支持情况仍待实测。

如果需要从 Chat Completions 改接 Responses，须明确列出新增 Adapter 的范围。Responses 可能在一次请求内返回多个独立消息和工具 item，必须保留 item 身份、顺序和各自 phase，不能塞进现有一个 content 字符串。当前仅有兼容接口时，不为了模仿 Codex 强行重建整个 Provider 层。

## 3. 消息归类与执行规则

### 3.1 原生用途优先，缺失时兼容

保留现有 ModelResponse 的 content、reasoning、toolCalls、usage、stopReason；增加可选 phase。对于当前每次请求只有一个聚合助手消息的路径，接口如下：

```ts
type AssistantMessagePhase = 'commentary' | 'final_answer';

// 合入现有 ModelResponse；只表示 Provider 实际提供的用途。
interface ModelResponsePhase {
  phase?: AssistantMessagePhase | null;
}

// ModelStreamEvent 增加一种元数据事件。
type MessageMetadataEvent = {
  type: 'message_metadata';
  phase: AssistantMessagePhase;
};
```

由 Adapter 读取真实协议元数据，不从正文解析标签，不往不支持的 API 塞 phase 参数。完成响应也要带回最终 phase，避免只在流里保留。

| 已知信息                       | 消息用途与来源               | 何时能确定位置                           |
| ------------------------------ | ---------------------------- | ---------------------------------------- |
| Provider 提供 commentary       | commentary / provider        | 元数据到达时；若早于文字，可从第一帧定位 |
| Provider 提供 final_answer     | final_answer / provider      | 同上                                     |
| phase 缺失，完整响应带工具     | commentary / compatibility   | 完整响应确定后                           |
| phase 缺失，完整普通回答无工具 | final_answer / compatibility | 完整响应确定后                           |
| phase 缺失且响应仍在流式生成   | 未知                         | 保留正文流式位置，不提前认证为最终回答   |

事件与投影保存可选 phase 和 phaseSource（provider / compatibility），避免把兼容推导冒充原生信息。原生字段不因后续 tool.call 被覆盖；工具是否执行由结构化调用及现有校验决定。

这是消息用途，不是成功证明。空响应、截断、取消和 Provider 错误继续使用现有异常与结束原因；不能因为文字归类为 final_answer，就隐藏这些状态。

旧事件没有 phase 时，共享投影根据同一步的工具调用恢复兼容分类。不能在 assistant.message 刚到、tool.call 尚未附着时，永久认定它是最终回答。该逻辑统一在共享投影处理，前端组件不分别猜测。

### 3.2 消息用途与生命周期分开

```text
模型返回说明 + Tool Call
→ 执行工具
→ 写入完整工具结果
→ 下一次模型请求
→ 模型继续调用工具，或者给出回答
```

现有 Queue、Steer、Cancel、审批、request_user_input、Compaction 和恢复语义保持不变。说明文字不构成执行事实，也不构成授权。

- 消息的完成事件只代表这一条消息结束；不能收到 commentary 的完成事件就关闭整个响应流。
- 同一个 Provider 响应仍在继续时，继续接收后面的消息或工具，不额外调用模型。
- Tool Call 驱动工具执行；final_answer 元数据不能使同一响应中尚待处理的合法工具被跳过。
- 响应结束后仍按工具后续需要、待处理输入等生命周期事实处理。本阶段不因 commentary 自动补一次请求。
- 原生 commentary 是完整响应的唯一输出、且没有其他继续条件时，保留其执行说明身份，显示“本轮已结束，未返回最终回答”，不能复制成最终答案或暗示任务成功。
- 如果选定的原生接口需要 end_turn 等信号来驱动后续请求，必须在该 Adapter 接入时一并核实和处理；只接 phase、漏掉必要继续信号的实现不能作为原生路径交付。

### 3.3 已知限制

如果模型没有提供 phase，只返回“我先检查一下文件”，没有工具调用，当前兼容流程仍可能将它作为回答结束。提示词和实际任务验证可以降低出现频率，但本次不声称解决它。

不增加“自动再问一次模型”的机制，也不根据“我准备”“接下来”等关键词判断继续。只有实际任务中证明这个问题频繁出现，才单独设计修复。

即使接入原生 phase，也不能仅凭这个字段保证模型最终完成任务。第一帧正确定位与避免提前结束是两个不同问题。

## 4. 提示词怎么改

### 4.1 保留原有能力规则

以 `src/runtime/model.ts` 的当前 MINIMAL_SYSTEM_PROMPT 为基线，保留工具真实性、必要事实询问、capability_search、Skill/MCP 渐进加载、memory-profile、工作区、产物和权限规则。

当前提示词已经要求直接完成任务和不编造工具结果，但没有明确规定执行说明的长度、频率与动作绑定。只增加下面这个固定片段：

```text
执行说明与回答：
- 能直接回答时直接完成。多步骤任务首次调用工具前，用普通正文说明目标和第一步。
- 遇到重要发现、假设变化、失败重试或阶段切换时，主动说明已知事实、对任务的影响和下一步；区分结论与待验证假设。即使已有模型推理，也要同步必要进展，让用户能判断方向并及时干预。
- 通常用 1–3 句，必要时补足依据；相关连续操作可合并说明，不逐工具播报、不编造发现、不展开内部推导。
- 需要操作时在同一响应中发出真实工具调用，不只说计划就结束；在已有授权内继续执行。
- 最终回答交付结果、必要依据和未完成事项，区分文件已生成与内容已核验；用户要求详细回答时正常展开。
```

用户明确要求详细分析或解释时，正常提供详细回答。过程说明以用户能够判断任务方向、依据和影响为先，不设置一两句话的上限，也不通过程序截断模型文字。

### 4.2 修改前后例子

| 场景       | 应避免的输出                                           | 目标输出                                           |
| ---------- | ------------------------------------------------------ | -------------------------------------------------- |
| 开始读文件 | “我需要全面考虑目录、编码、字段、异常和所有可能情况……” | “我先读取表头，确认要汇总的字段。”并调用 read      |
| 连续查询   | 每个工具前都重复“接下来我将……”                         | 一次说明相关查询，随后实际调用工具                 |
| 发现问题   | 复述全部 Tool Result，再展开多种猜测                   | “有三行日期格式不一致，我先核对这几行。”并调用工具 |
| 简单问答   | “我先分析一下这个问题……”                               | 直接回答                                           |

### 4.3 边界

- 不让模型在正文中输出 phase 字段、JSON 包装或自定义标签。已验证原生 phase 能力的路径可追加固定指令：“中途说明使用接口的 commentary 阶段，最终回答使用 final_answer；不要把阶段标记写进正文。”未支持的路径不追加。
- 连续沉默时允许在下一次已有主请求末尾附加临时提醒（见第 11 节）；不增加独立说明请求或计划工具。
- 固定 Prompt 变化按已有版本记录方式同步到 request.context；不重新设计整套提示词版本系统。
- metadata 和 compaction 继续遵循其专用输出要求，不套用过程说明。若摘要调用复用主请求前缀，确认末尾摘要指令明确只输出摘要。

## 5. 界面和数据怎么改

### 5.1 执行过程

当前 UI 以 reasoning 作为展示阶段边界。改为按 Step 组织：

```text
执行过程
  步骤 1
    我先读取表头，确认要汇总的字段。
    [read · 已完成]
    [模型推理 · 展开]  ← 仅实际有 reasoning 时提供

  步骤 2
    [bash · 已完成]    ← 没有说明也正常显示
```

最终回答放在正文。推理默认折叠，展开是视图行为，不改变推理配置、历史记录或 Provider replay。

### 5.2 流式输出

- 复用现有 requestId 关联流与完整消息，在消息投影中补齐该关联。
- 原生 phase 在文字前到达：commentary 从第一帧进入执行区域，final_answer 从第一帧进入正文。接收增量就展示，不等完整响应。
- 没有 phase：保留现在的正文流式位置。完整响应确认带工具后再将文字归入过程；回答留在原位，不先放进执行区域再搬出。
- phase 在文字开始后才到达：本次按兼容方式持续展示，待该消息完成后确定归位，避免生成过程中挪动文字。不能把这种接口宣称为支持第一帧定位。
- 同一段文字只渲染一份；取消时保留已有部分输出和取消状态，不留永远转动的加载图标。
- 原生 phase 在首个文字之前必须先进入持久事件与 Projection。以现有流关联为基础增加一个小型 assistant.message.metadata 事件，包含 requestId、stepId、turnId、phase；后续 chunk 和完成消息沿用同一关联。旧接口不需要发送这个事件。
- 不建立自定义文本协议或额外的说明模型。若首步核实选择了多 item 原生接口，需按第 2 节明确适配范围与 item 关联后再实现，不能直接复用单消息关联。

### 5.3 事件与历史

- assistant.message 增加可选 phase/phaseSource，ProjectedMessage 和流投影保留相应字段及 requestId；增加元数据事件的严格 Schema，沿用现有事件存储结构。
- 更新当前严格 Schema，允许新字段并接受旧数据缺失；不升级全局事件版本或数据库版本。
- 同一发布包更新 Worker、Contract 与 Renderer。新字段对旧日志兼容，不据此承诺旧二进制能读取新事件。
- 当前 Turn 继续保留模型文字、工具配对和所需 reasoning；折叠 UI 不删上下文。
- 历史 QA 复用统一消息归类，执行说明不被重复纳入最终问答。原生 commentary 即使没有工具也要排除，不能继续只用 toolCalls 数量判断；当前 Turn 则保留推进任务所需说明。
- 需要回传原生 phase 的接口在 Adapter 序列化时保留实际元数据；兼容推导的 phase 不回传成 Provider 事实。折叠推理不影响必需 reasoning replay。
- 原始事实和既有摘要不回写，不增加升级时模型调用。

## 6. 思考开关如何使用

复用当前“默认／关闭／开启”和 Provider 参数映射。本阶段不新增能力矩阵，不改变已有模型设置，也不全局更改新建模型默认值。

实施验证先保持用户当前推理设置，检查执行说明质量；高强度推理也应能产生简洁说明。若另行比较开启/关闭效果，再选择确认支持开关的模型并检查实际请求参数和任务表现。未知 Provider 不自动注入专用参数；服务端拒绝参数时保留错误，不静默回退后仍显示关闭。

当前 executeTurn 在 Turn 开始时读取模型快照，因此设置变化在下一 Turn 使用，不在工具循环中途切换。模型推理详情是否展开与这个开关独立。

如果之后实际验证证明某个模型关闭思考更合适，再单独调整其默认值，不把这项决策绑定到本次界面改造。

## 8. Example：完整交互

以下内容是设计示例，工具参数为简写，不是真实执行记录。

### Example 1：读取并汇总文件

```text
用户：统计 sales.csv 按地区的销售总额。

Step 1：普通输出“我先读取表头，确认地区和金额字段。” + read
        Runtime 标记 commentary → 执行说明和 read 卡片

Step 2：普通输出“字段已确认，接下来按地区汇总。” + bash
        Runtime 标记 commentary → 执行说明和 bash 卡片

Step 3：普通输出“华东 120 万，华南 95 万，华北 80 万，合计 295 万。”
        无工具 → final_answer → 聊天正文

总共三次主模型请求；不为生成执行说明多调用模型。
```

### Example 2：直接回答与无说明工具调用

```text
用户：CSV 是什么？
模型：直接解释 CSV。
结果：一次请求，只展示回答，没有空执行卡片。

用户：文件有多少行？
Step 1：无普通文字，只有工具调用。
Step 2：回答“共 128 行”。
结果：工具卡片正常显示，不强制编造说明。
```

### Example 3：关闭推理与中途取消

```text
关闭推理：模型仍可输出普通说明并调用工具，执行过程正常展示。
开启推理：普通说明照常展示，reasoning 位于默认折叠的详情中。

没有 phase 的流式文字先到：在正文显示一份文字。
完整响应带工具：这份文字归位为执行说明；不带工具的回答留在原位。
用户中途取消：保留已有文字和真实工具状态，显示已取消，不额外调用模型。
```

### Example 4：本阶段尚未解决的提前结束

```text
模型只输出“我先检查文件”，没有 Tool Call，也没有原生 phase。
结果：仍按当前兼容规则结束；不自动补请求。

实际验证时，这算任务未完成，不能因 Turn=completed 就认为执行成功。
```

### Example 5：原生 phase 从第一帧正确定位

```text
Provider 消息开始：phase=commentary
Adapter 发出 message_metadata；Runtime 持久化后投影到执行区域
Provider 文字增量：“我先” → “读取表头。”
UI：从“我先”开始就在执行区域逐字显示
Provider 后续发出工具调用 → Runtime 真实执行

Provider 后续回答消息开始：phase=final_answer
文字增量：“统计结果” → “如下……”
UI：从第一个文字片段开始就在正文显示，无需搬动
```

若同一响应含多条上述消息，必须使用对应原生 Adapter 的 item 关联；示例不表示当前聚合 Chat Completions 已支持多消息。新增模型请求是否需要发起取决于工具后续和原生生命周期，不由展示 phase 决定。

## 9. 验证与验收

只验证此次修改涉及的行为：

1. 简单问答一次请求完成；说明 + 工具 + 回答的调用次数、工具顺序与结果不变。
2. 有工具无说明、有说明无 reasoning、开启 reasoning 三种情况都能正常展示。
3. 流式内容完成后只出现一次；刷新、取消和历史回放后归属一致。
4. 旧事件缺失 phase 可以恢复；tool.call 晚于 assistant.message 到达不导致永久错分。
5. 当前 Turn 的工具配对和必要 reasoning replay 不变；历史不重复纳入执行说明。

### 可干预的进展说明：Prompt Revision 4

根据真实界面反馈，Revision 3 仍可能只产出“字段名和我猜的不一样，看一下实际结构”之类局部动作说明。用户无法据此判断目标、范围、交付或结论是否受到影响。本次取消一两句话的长度导向，优先保证说明足够用户判断，并在重要发现、方案变动、证据缺口及验证结果处持续更新。

- 开始时交代目标理解、范围、预期交付和重要假设。
- 推进时交代真实发现、阶段判断、对目标的影响和下一步验证。
- 改变范围、切换方案、替代数据或跳过检查前说明原因及影响；不增加每步等待用户确认的流程。
- 区分产物生成与内容核验，保留尚未完成事项。

## 11. 轻量进度沟通试用（2026-09-05）

按用户最新要求，将常驻“执行说明与回答”缩短为第 4 节的五条规则，Prompt revision 升为 6。保留首次行动前说明、重要发现及影响、下一步和最终交付要求，不要求每个工具都输出旁白，不固定业务模板。

- 当前 Turn 第一轮完成工具操作却没有非空普通正文时，就在下一次正常主模型请求末尾附加一条短 system 提醒；提醒若被忽略，之后每隔两轮沉默工具操作再提醒。自最近说明/提醒所在步骤开始已过 60 秒且已有工具轮完成时也可触发。时间用持久步骤开始时间近似，可能略早于真实正文输出时间；不打断正在运行的模型或工具。
- 推理字段、工具结果和其他 Turn 的正文不清除沉默计数。出现普通正文后重置；提醒被忽略时，也先间隔两轮操作或 60 秒再提醒，避免每次请求重复追加。
- 提醒只存在于该次请求，不写成聊天消息、工具结果或运行检查点。现有 `model.request.context.runtimeConfig.progressReminder` 记录是否实际附加，供投影重建及后续节流使用；旧事件字段缺失视为 false。
- 提醒进入 Context Projector 预算并计入 currentTurnTokens。必要上下文加提醒超过预算时省略提醒，不能挤掉工具配对或造成额外失败。metadata/compaction 不附加提醒；原有超上下文恢复重试保留同一次提醒意图。
- UI 只为已经发生的工具操作展示确定性运行状态，例如“正在执行：读取文件”或“已完成 2 项工具调用”。工具动作优先使用已有 presentation 标题，无法获得时才显示工具名。简单回答、等待模型、推理与正文输出不使用客户端硬编码说明，避免客户端替模型表达意图；计时只随真实工具状态显示。详情继续默认折叠。
