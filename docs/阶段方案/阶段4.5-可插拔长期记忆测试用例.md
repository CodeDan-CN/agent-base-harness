## 1. 测试目的

本测试文档验证以下阶段新增能力：

1. `read`、`write`、`edit`、`bash` 四个第一方工具按 Pi 产品面、dp-harness ToolDefinition 与能力分层完成 Schema、权限、执行、输出投影、取消和持久化，并替换本项目自定义 `host_command`。
2. Streamable HTTP 作为外部 MCP 主路径，stdio 作为本地与测试路径；两者都可以按用户配置、连接、初始化、发现、调用、动态刷新、恢复和释放。
3. 发现到的 MCP 工具先进入管理目录，只有已审核启用的工具进入下一 Step Snapshot。
4. MCP 工具名称、raw route、Schema digest、generation、审批、结果校验和上下文预算正确接入 Runtime。
5. 固定版本的默认 Memory MCP 可以通过通用 stdio MCP 链路离线完成工具发现、写入、检索、更新/删除和跨 Session 使用；远程替代 Server 使用 Streamable HTTP。
6. Client 不创建记忆专用 Provider、Skill 或 `memory_*` 包装工具；随包 Server 仍以独立 MCP 进程运行。
7. 两个用户的 MCP 配置、Credential、Catalog、连接、进程、Tool Event 和外部记忆数据严格隔离。
8. `capability_search` 一次同时检索 Skill 与 MCP 两类轻量目录，以同级候选交给 Agent 判断，并只对选中项加载正文或完整 Schema。

## 3. 进入与退出条件

### 3.1 进入条件

- 阶段 4 模型能力、Session/Event Summary 和 Surface Compaction 基线通过。
- 当前 Tool Registry、Skill、ProcessRunner、Credential 和双用户 Scope 测试通过。
- 四个工具的路径、文件观察、环境、dp-harness ToolDefinition 输出/展示 Contract、Skill 迁移和审批边界已冻结。
- MCP Server/Tool Schema、名称、审核状态和 `mcpRevision` 已冻结。

### 3.2 退出条件

- 全部 P0 用例通过。
- P1 用例无影响数据正确性、用户隔离和恢复的阻断失败。
- 无残留 MCP 子进程、临时文件、未清理锁、timer 或跨测试状态。
- 阶段 1～4 默认自动化继续通过。
- 完成一次打包前 MCP 资源路径和外部 Server 启动 Smoke。

## 14. 基线回归

阶段 4.5 改造后必须保持：

- 两个用户的 Session、模型、Skill、Credential、附件和 Runtime 配置隔离。
- Skill 目录/ZIP 安装、启停、`skill_load`、资源加载，以及迁移后的 `skill_load + bash` 脚本执行。
- 模型 Tool Catalog、Prompt、执行轨迹和公开 Contract 中不存在 `host_command`；底层 `ProcessRunner` 回归继续通过。
- OpenAI-compatible 流式文本、reasoning、usage、单/多 Tool Call 和结果回送。
- Queue、Steer、立即介入、Cancel、Interaction 和多 Session 并行。
- Session/Event Summary、Tool Result Pruner、Checkpoint、Surface Replace 和 overflow recovery。
- Client 流式 Markdown、Think/执行内容分离、执行卡唯一投影和用户切换。
- 不增加任何记忆专用核心表、Provider 或 Skill 隐式写入路径。

## 17. Go/No-Go 检查

满足以下全部条件才可进入阶段 5：

- 所有 P0 通过。
- `read`、`write`、`edit`、`bash` 四个第一方工具的安全边界和 Runtime 行为通过。
- `host_command` 已从模型 Tool Catalog、Prompt、执行路径和公开 Contract 删除，Skill 脚本通过 `bash` 完成回归。
- Streamable HTTP 主路径通过 JSON/SSE、Session ID、协议版本、结果、取消、动态刷新、恢复、安全和 UI 主链路测试；stdio 兼容通过等价 Tool Bridge 测试。
- 新工具默认关闭，Schema 变化会失效旧审核，运行中 Step 不发生定义/路由错位。
- 默认 Memory MCP 可以离线启动，并通过普通 MCP 配置、审核和调用流程完成跨 Session 验证。
- 不存在长期记忆正文进入核心 SQLite、记忆专用 `MemoryProvider`、`memory_*` 包装工具或 `user-memory` Skill 的 4.5 必需实现。
- 没有跨用户 Credential、Catalog、连接、目录、进程、调用、配置或外部记忆数据泄漏。
- 没有丢失更新、无界重连、假成功确认或残留子进程。
- 阶段 1～4 默认自动化无回归。
