## 对实现的含义

1. 当前生产 Adapter 仍固定发送 /chat/completions；已有的 phase 兼容读取不等于实现 Responses API。
2. 两家当前端点均已实测支持 /responses 及自定义工具回传，但本次没有表现出比 Chat 更多的过程说明。
3. 百炼 Responses 未提供 phase；DeepSeek 在 output_item.added 提供 final_answer，随后 message 的 output_item.done 改成 commentary。不能默认相信它在第一帧的用途标记。
4. 本次 Responses 的输出顺序均为 reasoning → message → function_call；更换协议并未使普通执行说明提前到推理之前。
5. 截图中的单步直接问答没有工具，按当前常驻规则会直接回答；运行状态属于确定性 UI 提示，不等于模型主动生成的任务意图。
6. 建议继续定位真实多工具任务的缺失步骤，再决定是否引入 Responses Adapter；不能把协议迁移当成说明覆盖率保证。

## 结构化进度工具实验

又给两家模型增加了一个 `progress_update(message)` 工具，并明确要求在同一响应中先记录进度、再调用实际工具。Chat 与 Responses 共 8 个工具步骤中，模型均未调用该工具，而是继续输出普通正文后调用实际工具。说明模型已经把自然语言过程说明视为首选表达；常驻一个额外工具 Schema 并不能提高本次覆盖率，因此不接入生产 Runtime。

最终采用两层方案：模型普通正文提供事实、影响与下一步；Runtime 只根据真实 Tool Call/Result 显示确定性工具状态，不为简单回答或模型推理生成硬编码说明。第一轮工具操作若没有普通正文，下一次已有主请求立即附加进度提醒；提醒被忽略后每隔两轮沉默操作再提醒，不新增模型请求。
